# Phase 15J-B — secure web edge deployment preview

Status: **implemented and locally tested; deployed in Phase 15J-C2**. This phase itself did not deploy Firebase Hosting, the web edge, or a new core API image, and did not run a browser cloud transaction. Phase 15J-C2 later deployed the reviewed web edge and core API image update; Firebase Hosting and browser cloud E2E remain pending.

## Ownership discovery and deployment prerequisites

`boundarymesh-dev` is the active GCP project. A read-only project description returned no `firebase:enabled` label. `firebase.googleapis.com`, `firebasehosting.googleapis.com`, and `identitytoolkit.googleapis.com` are not in the enabled-service list. Read-only Firebase Management, Hosting, and Identity Toolkit requests each returned HTTP 403. Those facts do not conclusively prove whether Firebase was linked earlier; they do prove that this workstation cannot currently inspect its Firebase project, Auth provider, or Hosting site through those APIs. No Firebase service agent or unrelated resource was imported or modified.

Before any 15J-C apply, an authorized operator must confirm whether `boundarymesh-dev` is already a Firebase project, whether a Hosting site/web app exists, and whether Google sign-in is configured. If the project is not linked, add Firebase to the **existing** GCP project through a separately reviewed step; never create a second project or adopt Google-managed service agents. Set up only the required Google sign-in provider and approved operator UID. The Firebase web app's public API key, auth domain, and project ID are needed for the final build; none is a service-account credential. The current Firebase 403 is a real deployment prerequisite, not an assumed success.

## Trust and identity boundaries

The static browser uses Firebase Authentication with in-memory persistence for an initial Google sign-in. It sends the short-lived Firebase ID token to the same-origin `/session/login` route, then clears Firebase client state. The separate Java/Spring `backend/web-edge` Cloud Run service verifies that token, requires recent sign-in and verified email, and checks an explicit server-configured UID allowlist. An empty allowlist denies everyone. It issues a one-hour Firebase-signed session cookie with `Secure`, `HttpOnly`, `SameSite=Lax`, and host-only `__Host-` semantics. Every request verifies the cookie with revocation checking and rechecks the allowlist. Logout revokes that user's Firebase refresh tokens and clears the cookie; this deliberately invalidates all of that user's Firebase sessions. The BFF responds with explicit unauthorized/forbidden/error states and no token body or stack trace.

`/session/bootstrap` sets a separate random, readable `__Host-bm_csrf` cookie. Spring Security's CSRF filter applies to every unsafe HTTP method, and login, logout, and transaction submission also require its value in `X-BM-CSRF` through a constant-time controller check. Same-origin Hosting rewrites and absence of cross-origin CORS permission keep an attacker from reading that cookie and setting the custom header from another origin. The BFF permits only exact session routes and five product API method/path pairs: POST transaction, GET delivery disposition, GET attestation summary, GET attestation verification, and GET audit-chain verification. It validates path IDs, rejects transaction bodies over 16 KiB, caps core responses at 64 KiB, and never forwards browser Authorization or identity headers. `/api/v1/dev/**`, admin, Microsoft, and arbitrary proxy paths remain denied.

The BFF's dedicated keyless `boundarymesh-web` identity obtains a short-lived Google-signed ID token with the core Cloud Run URL as audience. The core API receives only that service identity at its IAM boundary; it receives no `allUsers` or `allAuthenticatedUsers` binding. The BFF is intentionally public at Cloud Run transport so Hosting can rewrite to it, but its product routes require application session/authorization. The BFF has no Firestore, Pub/Sub, KMS, Secret Manager, or service-account-key permission. No human identity header is forwarded or invented in the core audit chain: current core transaction evidence truthfully describes the admitted IAM workload. Human attribution would require a separate validated provenance design.

## Production read model and SPA

The private core API now exposes a resource-specific `GET /api/v1/deliveries/{instructionId}` over `DeliveryStateQueryService` and the existing `DeliveryIdempotencyStore` port. It returns only instruction ID, exact terminal state, provider category, whether the provider was called, attempt count, and terminal flag. Unknown/malformed IDs return 404. The worker's durable D1-style `QUARANTINED`, `CREDENTIAL_OR_CONSENT`, `provider_called=false` state is representable; the controller has no Google SDK or raw Firestore dependency.

The existing attestation controller supplies a new safe, narrow `/{id}/summary` without credential references, raw signatures, payloads, or provider internals. Existing `GET /{id}/verify` and audit-chain `GET /{chainId}/verify` are reused. Production Spring security permits precisely those GET routes plus the existing transaction ingress and health/readiness. Collection lists, raw audit attributes, mutation verification methods, quarantine administration, and all `/api/v1/dev/**` remain denied.

The hosted Vite build uses `VITE_APP_MODE=cloud`. A build-time branch loads only the production console; its generated bundle contains no `/api/v1/dev/**` route and no private Cloud Run URL. The view initializes a BFF session, handles signed-out/unauthorized/expired/unavailable states, submits a controlled synthetic QuayForge→Rivertide `POST /api/v1/transactions`, displays the actual 202/decision/IDs, reads signed attestation and audit verification, and polls delivery at three-second intervals for at most about 30 seconds. A 404 means the worker has not recorded a terminal result yet. `QUARANTINED` with `provider_called=false` is shown as retained terminal custody, never as external success. Local labs remain available only in the local build.

## Hosting and infrastructure ownership

`firebase.json` serves `frontend/dist`. `/session/**` and `/api/**` rewrite to `boundarymesh-web` in `europe-west4` before `**` falls back to `/index.html`. Hashed assets receive immutable caching, the HTML entry is not cached, and the static response includes CSP, frame, content-type, referrer, and permissions policy. Dynamic responses are `no-store`. The CSP must be smoke-tested with the actual Firebase Google sign-in flow in 15J-C; no production Firebase app exists to exercise it in 15J-B.

Firebase project linkage, provider configuration, web-app registration, Hosting site ownership, and Hosting releases are deliberately **not** adopted into Pulumi while the Firebase APIs return 403. Hosting configuration is versioned in `firebase.json`; after ownership is established, 15J-C should use a pinned Firebase CLI and explicit `--project boundarymesh-dev` for the Hosting release. No `.firebaserc` implies that an unverified project/site already exists.

Pulumi defines six preview-only web-edge resources: a dedicated service account, service-level core API Invoker member, minimal custom Firebase session role (`firebaseauth.users.createSession`, `.get`, `.update`), its member, the Cloud Run BFF service, and `allUsers` Invoker **on the BFF only**. The existing 33 Phase 15I resources remain as managed. The preview image tag is deliberately not pushed, and `webOperatorUids` defaults to empty; Pulumi rejects any non-preview apply until a pushed immutable `webEdgeImage` digest and authorized UID are provided. 15J-C must also build/push a new immutable core API image containing the safe reads and preview its API update before apply. No image is pushed in 15J-B.

Configuration contract:

- Browser PUBLIC: `VITE_APP_MODE=cloud`, Firebase web API key, Firebase auth domain, Firebase project ID. `VITE_API_BASE_URL` is ignored in cloud mode; all app requests are same-origin. These values are not privileged credentials.
- BFF SERVER-SIDE NON-SECRET: Firebase project ID, core API service URL, comma-separated operator UIDs, `SPRING_PROFILES_ACTIVE=prod`. The UID list is operational authorization data and must be configured server-side, never from the browser.
- Infrastructure NON-SECRET: `webEdgeImage` pinned to a remote `@sha256:` digest before apply, `webOperatorUids` before apply. Current preview uses an intentionally unusable image tag and empty allowlist.
- SECRET: Firebase session cookies, CSRF tokens, browser sign-in ID tokens, and short-lived BFF→core ID tokens exist only at runtime. There are no static credentials, SA JSON files, Firebase Admin keys, Pulumi passphrases, or secret payloads in the frontend bundle, Pulumi config, or source.

## 15J-C deployment order and rollback

1. Resolve Firebase ownership/API 403 and confirm the actual site, web app, and Google sign-in provider; configure the one authorized operator UID. Review CSP against the real Firebase auth domain.
2. Re-run full backend/BFF/frontend/infra tests, Hosting rewrite validation, image context scan, and a fresh baseline Pulumi preview. Build one fresh core API image and one BFF image, smoke-test them, push only those two to the existing Artifact Registry, and resolve remote immutable digests. Build the static cloud SPA with the actual **public** Firebase web config and verify no dev routes, private API URL, source maps, or secrets are bundled.
3. Set the immutable BFF digest and operator UID in non-secret Pulumi config, update only the core API image digest, then inspect full and targeted previews. Apply only the reviewed BFF identity/IAM/service and core API update. Verify the core remains IAM-private and the BFF rejects unauthenticated, unauthorized, CSRF-less, and unallowlisted calls before exposing Hosting.
4. Deploy the `firebase.json` Hosting release to the confirmed site with explicit project selection. Verify deep links, static caching, headers, same-origin rewrites, Firebase sign-in, session expiry/logout, and BFF→core invocation. Only then run one controlled browser-origin synthetic transaction, verify evidence and terminal quarantine, inventory its application residue, and perform a separate cleanup/freeze gate. No external connector is expected.

Rollback uses the previous immutable core API revision, previous BFF revision, and previous Hosting release. Remove the new core Invoker binding if the web edge is retired. Do not change the Worker Pool or make the core API public.

The exposed Pulumi passphrase remains a known accepted credential-hygiene follow-up; no rotation occurs in 15J-B.
